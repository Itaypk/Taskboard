# Web UI internationalization (i18n)

Design for extending localization to the web UI. This is a design/handover document, not
current-state documentation: it records the high-level design, the decisions made and their
rationale, and the key components to build. Concrete implementation details (exact key names,
component-by-component changes) are left to the implementing team.

## Where we are today

Localization already covers the *communication channels* end-to-end:

- **Telegram and email copy** goes through Spring `MessageSource` (`messages*.properties`,
  ~110 keys), rendered server-side with the locale from
  `UserSettingsService.getLocale(userId)` → `user_settings.preferred_language`.
- **LLM output** (planning conversation, reminders, task suggestions) is instructed via prompt
  templates to respond in `{{preferred_language}}`, with the user's gender setting for gendered
  languages.
- **User content** in the web UI (task titles, notes) already renders correctly in any script:
  per-block `dir="auto"` in the note editor and `marked-bidi` in the markdown renderer.

What is *not* localized is the web UI chrome itself: every label, button, tooltip, empty state,
toast, and date format in `tasker-frontend/` is hardcoded English. There is no i18n framework on
the frontend. Additionally:

- `user_settings.preferred_language` is `NOT NULL` with default `"en-US"` — it exists for every
  user, but for most it was never an explicit choice.
- The settings picker offers 14 languages (`UserSettingsService.SUPPORTED_LANGUAGES`); actual
  usage across the beta user base is English and Hebrew only.
- The bundled fonts (Fraunces, Plus Jakarta Sans, IBM Plex Mono) are Latin-only.
- Backend error messages (`ProblemDetail.detail`, `{error: …}`) are English and shown verbatim
  in the error toast.

## Goals and non-goals

**Goals**

1. Fully localized web UI (strings, dates, plurals, text direction) in a trimmed set of
   languages, driven by the same per-user language preference the channels already use.
2. First-class RTL support (Hebrew, Arabic) — not a best-effort mirror.
3. A single, coherent locale resolution story across all surfaces (web, email, Telegram, LLM),
   so a user is never addressed in different languages by different channels.
4. A sustainable translation workflow for a solo project: English as source of truth, safe
   fallbacks, automated guards against catalog drift.

**Non-goals**

- Geo-IP locale guessing.
- Localizing the static `index.html` / SEO surface (crawler fallback content, meta tags stay
  English; see [What deliberately stays English](#what-deliberately-stays-english)).
- Translating the legal pages (ToS, privacy policy).
- Localizing admin-facing output (feedback emails, logs) — explicitly English today, stays so.
- A translation-management platform (Crowdin etc.) — overkill at this scale.

## Decisions

### D1. Trim the supported-language list to en, he, ru, ar

The picker shrinks from 14 entries to: **English (US), English (UK), Hebrew, Russian, Arabic**.
Rationale: every added language now carries UI-translation and QA cost, not just ~110 bundle
keys. Actual users today use only English and Hebrew; Russian and Arabic are the strategic next
two. The two English variants stay because they cost nothing (same strings; the region tag only
affects `Intl` date/number formatting and is already stored per user).

Mechanics:

- Shrink `UserSettingsService.SUPPORTED_LANGUAGES`; the settings picker follows automatically
  (it is fed from `SettingsOptionsResponse`).
- **Do not delete** the dormant `messages_de/es/fr/it/ja/ko/nl/pt/zh.properties` bundles. They
  keep working for any stored preference that still points at them (validation only runs on
  *new* settings updates), and they are a head start if a language is ever re-added. They
  receive no new keys — `MessageSource` falls back to the base (English) bundle per key, which
  is the desired degradation.
- Owner has confirmed no existing user has a removed language selected, so no data migration is
  needed. Defensively, the settings form must not crash if it ever encounters a stored value
  outside the list (render it as an extra option or fall back to English; implementer's choice).

### D2. Locale resolution: stored preference is authoritative; browser locale feeds it at registration

The requested chain — *user preference → browser locale → English* — is kept, but with a
refinement about **where the browser tier lives**. Rather than evaluating the chain on every
page load, the browser locale is consulted **once, at account creation**, to initialize
`preferred_language`; from then on the stored preference is the single authority for every
surface. Concretely:

| Surface | Locale source |
| --- | --- |
| Web UI, authenticated | `preferred_language` (from the bootstrap API response) |
| Web UI, anonymous (login page, magic-link/verify/invite pages) | best match of `navigator.languages` against the supported list, else English |
| Email, Telegram, LLM prompts | `preferred_language` (unchanged) |
| Pre-auth email (magic link to a not-yet-registered address) | best match of the request's `Accept-Language` against the supported list, else English — today this silently falls back to English, which is a small existing gap this design closes |
| New-user registration (all flows: Telegram OIDC callback, magic-link consumption, demo login) | initialize `preferred_language` from the request's `Accept-Language` best match, else keep the `en-US` default |

Why initialize-at-registration instead of a live three-tier chain (or a nullable
`preferred_language` with an "Auto" option):

- Email and Telegram have no browser to consult, so a live chain can't apply to them anyway. A
  nullable preference would force every existing `getLocale` call site to grow a fallback
  branch for marginal benefit.
- Initialization gives cross-channel consistency from day one: the first email a Hebrew user
  receives is already in Hebrew, matching the UI they signed up in.
- All registration flows pass through a browser request (even Telegram login is a redirect flow
  that starts and ends in the user's browser), so `Accept-Language` is always available.

Notes:

- **Existing users** all carry the stored `en-US` default, including Hebrew speakers. They will
  see English UI until they flip the setting — exactly what they see today, so no regression;
  at the current user count a one-line heads-up to the beta users is enough.
- **Demo login** counts as registration and gets the same initialization — the demo is the
  funnel, and a Hebrew-speaking visitor should see the demo in Hebrew.
- **Anonymous flash**: the SPA learns the authenticated locale only after `GET /api/auth/me`
  returns. Cache the last resolved locale in `localStorage` and apply it immediately on boot to
  avoid a language flash for returning users.
- No language switcher on the login page in the first iteration — browser detection covers it.
  Cheap to add later (a `localStorage` override slotted above browser detection).

### D3. Frontend framework: i18next + react-i18next, separate catalogs from the backend

**Library.** Use `i18next` with `react-i18next`. Rationale over the alternatives:

- *Hand-rolled `t()`*: tempting for a dependency-light project, but Russian (3 plural forms)
  and Arabic (6) make pluralization the trap that justifies a library. i18next delegates to
  `Intl.PluralRules` and this problem disappears.
- *react-intl / FormatJS*: brings ICU MessageFormat, which our copy doesn't need; heavier API.
- *Lingui*: compile-time extraction is elegant but adds build tooling to a Vite setup that is
  deliberately plain.

react-i18next is the boring, mature default: two runtime deps, JSON catalogs, React context
integration, per-key English fallback built in.

**Catalogs stay separate from the backend bundles.** Frontend UI strings live as JSON under
`tasker-frontend/src/locales/<lang>/…`, per-locale, loaded as lazy Vite chunks (dynamic import)
so an English user never downloads Arabic strings. The Spring `.properties` bundles continue to
own channel copy. No shared-catalog machinery: the two string sets serve different consumers,
overlap barely at all (~110 channel keys vs an estimated 400–600 UI strings), and use different
interpolation syntaxes. What *is* shared is terminology — keep a short translators' glossary
(task, board, backlog, plan, slot, category, tag…) as a section in this doc or a sibling file,
so the UI and the Telegram bot never call the same concept two different things in one language.

**Language codes.** UI catalogs are per-*language*: a single `en` catalog serves both `en-US`
and `en-GB` (the region tag still reaches `Intl` for date formatting). i18next's language
fallback (`he` → `en`) handles missing keys, so a partially translated catalog degrades to
English rather than to raw keys — this is also the mechanism that makes gradual translation
safe.

**Bootstrap.** The SPA needs the locale before first meaningful paint. Expose
`preferredLanguage` on the auth bootstrap response (`GET /api/auth/me` via `MeResponse`) —
today it only lives on the settings endpoint, which is fetched lazily when the settings modal
opens. Changing the language in settings applies immediately (`i18next.changeLanguage` +
flipping `document.documentElement.lang/dir`) — no reload.

**Language names in the picker** should become endonyms ("עברית", "Русский", "العربية") once
the UI is localized — render them on the frontend (from the catalog or `Intl.DisplayNames`)
keyed by the backend-provided codes; the backend `LanguageOption.label` stays as an
English-readable fallback.

### D4. Dates, numbers, and plurals through `Intl` with the active locale

All date formatting already goes through `toLocaleDateString`/`toLocaleTimeString`, but with
`undefined` or a hardcoded `'en'` locale (`utils.ts`, `StatsModal`, `ScheduleTaskModal`,
`WeeklyPlanDrawer`, `BoardSettingsModal`). Route them through a small shared helper that takes
the active *full* locale tag (`en-GB`, `he`, …). Behavior notes:

- `hour12: false` is currently forced. Recommendation: drop it and let the locale decide
  (he/ru/ar are 24h natively; `en-US` users get 12h, which is the correct localization). If the
  team prefers keeping planner times uniform at 24h, that's acceptable — decide once, document
  in the helper.
- Weekday/month names come free from `Intl`; no month-name strings belong in catalogs.
- `weekStartDay` remains an explicit user setting — do not silently derive it from locale.

### D5. RTL is a first-class deliverable, shipped with Hebrew

Hebrew and Arabic require full mirroring, not just translated strings. This is the largest
single work item in the project. Components:

- **Document direction**: set `dir` and `lang` on `<html>` from the active locale at runtime
  (RTL for `he`/`ar`). Everything below assumes layout responds to the `dir` attribute.
- **CSS logical-properties pass**: audit `index.css` (~1,600 lines) and ~40 CSS modules,
  converting physical properties (`margin-left`, `padding-right`, `left/right` offsets,
  directional `border-radius`, `text-align: left`) to logical equivalents
  (`margin-inline-start`, `inset-inline-end`, `text-align: start`, …). Deliberate exceptions —
  things that must *not* mirror — get a comment: the washi-tape/post-it decorative rotations,
  mascot artwork placement, and anything anchored to imagery rather than reading order.
- **User-content bidi already works** (per-block `dir="auto"`, `marked-bidi`) and must keep
  working in both directions: Hebrew UI with English task titles is the exact mirror of today's
  English UI with Hebrew titles. Don't set a global direction on user-content containers;
  leave them `auto`.
- **Fonts**: the current trio (Fraunces, Plus Jakarta Sans, IBM Plex Mono) has no Hebrew or
  Arabic glyphs; unhandled, browsers will render fallback system fonts that clash with the
  hand-crafted paper aesthetic. This needs a deliberate font choice per script (e.g. the Noto
  family, or curated system stacks) added to the font-face stack, **including a
  display/handwritten-feel companion for the post-it look** — flagging explicitly: this is a
  product/design decision, not just engineering, and should be made early in the Hebrew phase.
- **Drag & drop** (`@dnd-kit`) and any keyboard-arrow interactions need explicit RTL testing;
  horizontal gesture semantics may need flipping.
- Directional glyphs baked into strings or components (arrows "→", chevrons, back buttons)
  need an audit; prefer CSS-mirrorable icons over characters in catalog strings.

### D6. Error messages: localize on the client, keyed by stable codes; server text stays English

Today the toast shows server-sent English text (`detail`/`error`/`title`), with client-side
generic fallbacks per status class. Localizing *server*-generated messages would require locale
plumbing through every exception handler for text the user sees only in edge cases. Instead:

- The client-side generic fallbacks (in `api.ts`) and all flow-specific client messages move
  into the catalogs — that alone localizes the common failure UX.
- For server errors the user is *expected* to hit (validation, rate limits, blocked domains,
  invite conflicts), extend the existing machine-readable `code` mechanism (already present on
  `ApiError` and used by the import flow): the frontend translates known codes and falls back
  to the raw English server text for unknown ones. Codes are added opportunistically, per
  flow, as part of translating that flow — not as a big-bang backend sweep.
- Bean-validation field messages follow the same rule: the client already renders per-field
  errors and can key friendly localized text off the field name + code, with English
  server text as fallback.

### D7. Gradual by engineering, atomic per language launch

Extraction can and should land in many small PRs (screen by screen), because untranslated keys
fall back to English invisibly. But a *language* is only added to the picker's UI-effect once
its catalog is complete and (for he/ar) RTL passes QA — a half-Hebrew screen is worse than an
English one. Concretely: the UI language resolution maps any not-yet-launched language to `en`
for *catalog* purposes while comms keep using it, so the existing behavior (Hebrew emails +
English UI) remains the intermediate state throughout the rollout, and nothing ever regresses.

### D8. UI copy is gender-neutral in gendered languages

Existing project rule, restated because it now applies to a much larger string surface: Hebrew
and Arabic UI strings must be phrased gender-neutrally (infinitives, imperatives-avoidance
tricks, plural address — translator's choice per string). The user's gender setting remains an
LLM-conversation concern only; catalogs must not fork on gender.

## What deliberately stays English

- **`index.html`**: the static shell, meta tags, and the hidden prerendered crawler content.
  Serving per-locale documents would require server-side rendering/templating of the SPA shell
  for marginal SEO value. The SPA sets `lang`/`dir` at runtime.
- **Legal pages** (`tos.md`, `privacy-policy.md`): translated legal text carries liability
  nuance; the English version stays the only authoritative one. Optionally add a one-line
  localized notice ("This document is available in English only").
- **Admin-facing output**: feedback emails (already documented as English-only), logs, metrics.
- **Dormant language bundles** (D1): frozen, not deleted.

## Key components (summary for the implementing team)

Backend (small):

1. `UserSettingsService.SUPPORTED_LANGUAGES` trimmed to 5 entries (D1).
2. Registration-time locale initialization: `initializeForNewUser(userId, localeHint)` where
   the hint is resolved from `Accept-Language` in each login/registration entry point
   (Telegram OIDC callback, magic-link consumption, demo login) (D2).
3. `MeResponse.preferredLanguage` (D3 bootstrap).
4. Pre-auth magic-link email localized from `Accept-Language` (D2).
5. Opportunistic `code` fields on user-facing error responses (D6).

Frontend (the bulk):

1. i18next setup: init module, locale detection order (me-response → localStorage cache →
   navigator.languages → en), lazy per-locale catalog chunks, `changeLanguage` wiring in the
   settings modal, `lang`/`dir` document attributes.
2. String extraction: ~60 components' worth of literals into `en` catalog(s), including
   aria-labels, `title` attributes, and `document.title` if localized. See
   `docs/I18N-INVENTORY.md` for the per-component checklist and progress.
3. Shared `Intl` date/number formatting helper replacing ad-hoc `toLocale*` calls (D4).
4. RTL pass: logical-properties CSS migration, font stacks per script, dnd/gesture QA (D5).
5. Translated catalogs: `he`, then `ru`, `ar`.

Guard rails / testing:

- A Vitest check asserting key parity between the `en` catalog and each *launched* language
  (missing keys fail CI for launched languages; extra keys fail everywhere).
- i18next configured to fall back to `en` (never raw keys) in production, but to log/warn on
  missing keys in dev.
- Consider `eslint-plugin` rules against untranslated JSX literals once extraction is done, to
  stop regressions; skip if too noisy — the codebase is small enough for review to catch these.
- RTL visual QA checklist as part of the Hebrew phase (board, drawers, modals, drag & drop,
  toasts, settings).
- Optional: a pseudo-locale for layout-stress testing; nice-to-have, not required.

## Phased rollout

**Phase 0 — trim (independent, ship any time).** D1: shrink the language list; verify the
settings form tolerates out-of-list stored values. No user-visible change for current users.

**Phase 1 — infrastructure + extraction (no visible change).** i18next setup, locale
resolution incl. registration initialization and `MeResponse` change, `Intl` formatting helper,
string extraction to the `en` catalog across all components (multiple PRs), key-parity test.
The app looks identical when this phase completes; it is merely translation-ready.

**Phase 2 — Hebrew + RTL (first visible payoff).** Hebrew catalog, full RTL pass (CSS logical
properties, fonts — including the design decision on Hebrew display type), dnd/gesture QA,
launch `he` as a UI language. This serves the actual existing user base.

**Phase 3 — Russian, then Arabic.** Russian is a catalog-only launch (LTR, plural-rules
already handled by i18next). Arabic reuses the entire RTL investment plus an Arabic font stack
and its own QA pass.

**Deferred / ideas backlog** (move to `docs/IDEAS.md` on adoption): login-page language
switcher, localized `document.title`/meta, localized legal-page notice, broader server-error
code coverage, re-adding dormant languages.

## Open questions

1. **Hebrew/Arabic typography** (D5): which fonts preserve the paper/post-it aesthetic? Needs
   a product decision with visual prototyping early in Phase 2.
2. **12h vs 24h times** (D4): follow locale (recommended) or keep uniform 24h?
3. **Translation authoring**: the existing channel bundles suggest an LLM-assisted,
   owner-reviewed workflow. That scales to the UI catalogs for languages the owner can review;
   for the rest, decide between a trusted reviewer, a launch-and-report feedback loop (the beta
   audience is small and forgiving), or deferring that language's launch.
