# CLAUDE.md — `tasker-frontend/`

Conventions for the React SPA. Repo-wide guidance lives in the root `CLAUDE.md`; environment
variables are catalogued in `docs/CONFIGURATION.md`.

- **Keep the anonymous first paint small.** `App.tsx` is a thin route shell: `AuthContext`, `LoginPage` and `AppFooter` are the only eager imports. The whole signed-in surface lives in `Board.tsx` and every other route is a `React.lazy` chunk, because the landing page is what a cold visitor (and every PageSpeed/crawler run) downloads — before the split it carried drag-and-drop, all the modals, the markdown renderer and the policy texts, and the mobile FCP/LCP showed it. New signed-in UI belongs in `Board.tsx` or a chunk it pulls in; a new route goes behind `Lazy` unless it is genuinely part of the anonymous entry path. Watch the `dist/` chunk list after a build — a new eager import in `App.tsx` shows up as growth in the entry chunk.
- **Web fonts are fully self-hosted, not linked.** `src/fonts.css` (generated by `tools/refresh-google-fonts.sh`, imported at the top of `src/index.css`) holds the `@font-face` declarations, and the woff2 files themselves live in `src/assets/fonts/` (also generated by that script) — `index.html` has no `<link>`/`preconnect` to `fonts.googleapis.com`/`fonts.gstatic.com` at all. Same-origin removes a render-blocking third-origin round trip and a per-visitor request to Google on every page load; the ops-repo CSP (`itayp_dev/ansible/group_vars/all/main.yml`, `tasks` service) has no googleapis/gstatic allowance to match. Do not reinstate a `<link href="fonts.googleapis.com/css2?…">` or point `font-src` back at gstatic. Adding a family or weight means editing `FAMILIES` in the script and re-running it, not hand-editing `fonts.css` or `assets/fonts/`.
- **Static content pages** (`/terms`, `/privacy`, `/about`, `/faq`) are English-only markdown files in `src/auth/` imported with `?raw` and rendered through the shared `PolicyPage` shell; `{{APP_NAME}}` / `{{APP_URL}}` / `{{SUPPORT_EMAIL}}` / `{{ABUSE_EMAIL}}` are substituted at render time from the instance's config (`useBranding()`; the URL is the page's own origin) — never write the product name or host literally. The server also renders the same files into the HTML document for clients without JavaScript (`ContentPage` / `IndexHtmlController`, with its own title, description and canonical URL; `processResources` copies `src/auth/*.md` onto the classpath), and on a direct visit the route keeps showing that markup while its chunk loads (`LazyContentPage` + `src/prerendered.ts`). Adding one means: the markdown file, an export in `PolicyPage.tsx`, a `LazyContentPage` route in `App.tsx`, a `ContentPage` entry plus its path on `IndexHtmlController.contentPage`, a `<url>` in `static/sitemap.xml`, a line in `static/llms.txt`, a link in `components/AppFooter.tsx` (the site-wide footer, rendered once below `<Routes>` so it reaches signed-in and signed-out views alike), and `policyPage.*Title` / `footer.*` keys in **all four** locale catalogs.
- **Styling: co-located CSS Modules for component-specific styles.** New components add a sibling `Foo.module.css` and import it as `import styles from './Foo.module.css'`; reference classes via `styles.title` / `styles.demoBtn`. Use camelCase keys. `src/index.css` is reserved for design tokens (CSS custom properties), base element styles, and genuinely shared utilities (`.link-btn`, etc.) — don't add new component-specific rules there. See `auth/LoginPage.module.css` for the pattern. (The content pages' `.content-page` is a deliberate global exception: the server renders the same markup.)
- Auth-aware shell in `src/App.tsx`: `AuthProvider` (in `src/auth/AuthContext.tsx`) runs `GET /api/auth/me` on mount. `LoginPage` offers username/password (operator-listed users), Telegram (an outlined button that navigates to the OIDC redirect flow at `/api/auth/telegram/start`), passwordless email (inline form → magic link), a sandbox/demo button, a Google button (stubbed "Soon"), and a dev-login button gated on `import.meta.env.DEV`; which of the first four render comes from the instance config the server inlines into `index.html` (`src/publicConfig.ts`, read synchronously; hosted defaults when the block is absent, e.g. under `npm run dev` or in tests). It surfaces `?telegramLogin=failed|unavailable|closed` callback notices (auto-opening the modal). `SettingsModal` has a "Connected accounts" section (`ConnectedAccounts.tsx`) to link Telegram (navigates to `/api/auth/telegram/link/start`, surfaces `?telegramLink=…`) / unlink methods. The display name degrades gracefully for channel-less users (`UserMenu`: display name → telegram → email → "Account").
- **Transient, bottom-anchored UI goes through the one toast stack.** `notifyToast` (`src/toast.ts`) raises a toast; `components/ToastStack` is the only listener and the only fixed layer, and it also renders API errors (`notifyError` in `api.ts`) and the redeploy nudge. Don't add another fixed banner — two of them overlap each other and the account-claim band on a phone, which is what this replaced. A toast can carry one action ("Undo", "Refresh") and a `key`, so repeats replace rather than stack.
- `src/api.ts` wraps `fetch` with `credentials: 'include'`, echoes the XSRF cookie as `X-XSRF-TOKEN` on mutating requests, and dispatches an `auth:unauthenticated` event on 401 so `AuthContext` can flip to the login page.
